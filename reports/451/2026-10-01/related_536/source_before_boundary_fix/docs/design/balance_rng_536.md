# #536 흑랑 밸런스 전투 난수 재생

## 사양

`balance_boss`의 Lv3·Lv5 각 판은 **실제 명중 굴림을 유지**하되 도호 `PlayerCombat._rng`, 흑랑 `Enemy._rng`, 보스 층 기존 파수 박쥐 둘, 흑랑 P2 소환 박쥐 둘의 `_rng`를 판마다 독립된 고정 스트림으로 시작한다. 기존 지도 시드만으로는 몸들의 `_ready.randomize()`와 영속 도호의 `reset_session()` 뒤 남은 난수 상태를 고정하지 못해 같은 런타임 코드에서도 Lv3 세 판이 전부 지는 전체 검사 실패가 있었다. 게임의 난수 초기화·수치·스탯·명중 확정 스위치를 바꾸지 않는다. 기존 `ATTEMPTS=3`, 탕약 3, 한 판 45초, 최소 8초, Lv3/Lv5 승패·대가 판정과 보스 타깃 유지·참격 쿨마다 시도·생명35% 아래 탕약·`GameClock` 전투 시간을 유지한다. 기존 파수도 층 입구에서 깨어 보스 곁까지 추격하고 참격에 맞을 수 있으므로 삭제·재움 없이 포함한다.

## 실행 전에 확정한 시드

부모 지휘가 첫 실행 전에 승인한 기준은 `base = E2e.SEED = 20260916`이다. 정수식은 `seed = base + level * 1000003 + attempt * 10007 + role * 1009 + spawn_ordinal * 101`. `attempt`는 벌 안에서 1부터, `role`은 도호 1 / 흑랑 2 / P2 박쥐 3 / 기존 파수 박쥐 4다. 도호·흑랑 ordinal은 0, P2 박쥐는 실제 소환 순서 1·2, 기존 파수는 `map.guard_cells` 순서 1·2다. `DungeonLevel._spawn_enemies`의 preset 루프가 그 칸 순서로 `_spawn_one`을 호출하는 계약을 쓰고, ready 뒤 실제 위치가 해당 칸인지 검산한다. 위치는 `add_child` 뒤에 대입되므로 ready 시점의 임시 원점으로 ordinal을 뽑지 않는다. 초기 4몸과 P2 2몸, Lv3/Lv5 세 판씩 총 36개 독립 시드다.

시계·ObjectID·노드 이름·이전 대본 소비량·전역 난수를 파생식에 넣지 않는다. 첫 focused의 잠금 대기만 취소했으며 전투는 미실행이었다. 그 뒤 파수 role4를 추가한 것은 빠진 실전 몸 보완이며, 기존 base·식·role1~3 시드는 그대로다. 결과를 보고 시드를 검색하거나 다시 고르지 않는다. 첫 완전한 고정 묶음이 기존 판정에 실패하면 그 결과를 기록하고 밸런스 문제와 시험 재현성 문제를 구분한다.

## 채택 구조·대안

시험 전용 `tests/fixtures/balance_combat_rng.gd` Node를 `go_down` 전에 Main 자식으로 붙여 도호부터 고정한다. `SceneTree.node_added`에서 지정한 지역·보스 층의 `DungeonLevel`을 잡고 그 층의 기존 파수·흑랑과 P2 박쥐만 관찰한다. `ready` 동기 콜백에서 공개 `Enemy.seed_rng`로 첫 물리 틱의 겹침 분리·돌격·공격 난수 소비 전에 고정한다. 각 스트림의 seed·초기 state·종료 state를 로그에 남긴다. 판 끝과 준비 실패의 return에서는 명시적으로 종료하고, 대상 층 `tree_exiting`·다음 마을/다른 지역 `level_loaded`·대본 소멸·Main 종료도 원래 seed/state 복원과 `node_added`·`ready`·수명 신호 연결 해제를 맡는다. 입장 전 대본이 끊겨도 다음 대본의 리셋 경계에서 남은 도호 고정 스트림이나 관찰 연결을 제거한다.

이 구조는 게임 몸의 초기화 계약과 파수 AI를 유지한 채 실제 생성 순서를 검증한다. 대안인 전역 `seed()`는 몸별 private RNG를 잡지 못하므로 기각했고, 게임에 시험 시드/명중 확정 분기를 더하는 방식은 출시 동작을 바꾸므로 기각했다. 보스 층 도착 뒤 설치하면 파수의 첫 소비를 놓치므로 입장 전 설치를 채택했다. 승패를 통과시키는 시드 검색·재시도 확장·판정 완화도 하지 않는다.

## 검수

`tests/test_balance_rng.gd`는 실제 PlayerCombat·흑랑 층의 기존 파수 둘·실제 P2 소환 박쥐의 첫 소비 전 초기 상태, 실제 명중·피해 굴림 재생, 6개 스트림 분리, reset/restart 재시작, 판 끝 원래 상태 복원과 층 종료·입장 전 조기 실패 정리를 검사한다. `balance_boss` focused를 같은 첫 묶음으로 두 번 실행해 초기 seed/state 및 판별 승패·받은 공격/명중·파수·소환·종료 state를 비교한다. raw 전문은 자리 `._tmp/536_*.raw.log`에 보존한다. 매 실행 종료 직후 user:// 상세 Godot 로그도 별도 복사하고 첫 복사를 끝낸 뒤 둘째 실행을 시작한다. 전체 회귀는 지휘의 #451·#535·#536·#133 최종 스택 검사 한 번으로 수행한다.

재현 비교에서 파수의 입장/물리 틱 차이를 구분해야 할 때 파수2만 입장 직후·KEY_V 전후·종료의 state·XZ·pack_id·타깃·경로·physics tick·RNG.state를 관찰한다. 보조 표본은 0.5게임초 간격, 판마다 최대96줄이다. 관찰은 값을 읽고 로그만 쓰며 추가 draw·강제 wake·타깃 대입·위치/AI 변경을 하지 않는다. 단위에서 관찰 전후 여섯 RNG 상태가 동일한지도 검사한다.

준비 입력은 이 대본 안에서만 physics_frame 경계에 동기화한다. 실제 `InputEventKey` press/release는 기존 `E2e._key_state` 경로를 사용하며 press→release는1틱, 층 내려가기 키별 총6틱, V 접근 준비 총5틱으로 첫 동기화 실행 전에 고정한다. 원래 준비 process 대기의 실제 관측 범위(층 입장6틱, V준비4/5틱)에 맞춘 값이며 승패를 보고 조절하지 않는다. 공통 `E2e.frames/key`, GameClock·수치·45초/8초/세 판·승패 판정은 유지한다. 준비마다 실제 physics tick 차이를 검사하고, 단위에서는 실제 입력 이벤트의 press/release와6/5틱을 관찰한다.

준비6/5틱을 고정한 뒤에도 같은 V 전후 상태에서 P2 진입/종료 시각과 파수2의 접촉·종료 RNG가 달랐다. 공통 `E2e.frames(6)`은 process_frame6회를 세지만 전투 몸은 physics_frame에서 움직이고 공격을 처리한다. 따라서 이 대본의 while 안 대기만 로컬 physics_frame6틱으로 교체한다. 숫자6은 그대로 고정하며, 통과를 위해 다른 틱 수를 찾지 않는다. 기존 process6회는 headless 약128fps일 때 약0.047초(고정 시간 아님), 새 physics6틱은 60Hz·time_scale1일 때0.1초다. 이는 시험의 입력 확인 주기를 고정하는 변경이며 평타/스킬 쿨·명중률·AI·GameClock·45초/8초/세 판·승패/대가 조건은 바꾸지 않는다. 매 판 전체 입력 대기의 실제 간격6틱 여부·횟수를 기록하고, 단위는 실제 InputEventKey 두 이벤트 사이6틱을 검증한다. 이 완전 동기화 구조의 첫 묶음을 두 번만 실행해 역할별 초기/종료 state·공격/명중·승패를 비교하고, 차이 또는 패배가 남으면 그대로 보고한다. 전역 FPS 제한이나 게임 AI 타이머 재설정은 다른 대본/런타임을 바꾸므로 채택하지 않는다.

준비 키는 `_key_state`로 만든 실제 InputEvent를 press/release 직후 각각 공개 `Input.flush_buffered_events()`로 전달한다. 물리 대기가6/5틱이어도 입력 누적 버퍼가 층 생성 이벤트를 한 틱 늦출 수 있으므로 같은 물리 경계에서 전달까지 끝내야 한다. 실제 `_input` probe에서 release 전달 전후와 틱 간격을 확인했으며, 실제 Main/DevKeys에 ] 키를 넣어 `level_loaded`와 press가 동일 틱인지 검증한다. 직접 `load_area`·텔레포트·wake/타이머 조작은 하지 않는다. 공통 입력 helper와 입력 누적 설정도 바꾸지 않는다.

## 최종 집중 검수와 관측 한계

실제 몸/명중/스트림 분리/원상 복원/조기 실패 정리와 실제 Main/DevKeys 키 입력 단위는 **45/45 PASS(exit0)**다. 실제 ] press/level_loaded는 각각 tick37/37·44/44, release는38·45였고 V press51/release52 및5틱 준비, 전투 입력 probe30→36의6틱을 확인했다. 단위의 종료 ObjectDB/ResourceCache 보고는 기존 test.ps1 허용 항목이며 raw도 보존한다. 최종 단위 raw는 `._tmp/536_balance_rng_input_sync_unit_2.raw.log`와 같은 이름의 `.godot.raw.log`다.

입력 flush 구조의 첫 focused 두 회는 **30/30 PASS(exit0)**다. Lv3/Lv5 각 첫 판의 실제 여섯 몸, 총12개 initial/final state·시드가 두 회 모두 일치한다. Lv3는 공격41/명중25·생명130→34·최저32·탕약3·승리, Lv5는37/24·150→45·최저45·탕약3·승리로 같으며 파수/소환도 각각2마리다. 준비6/5틱과 전투의 각 대기6틱도 같았다. stdout와 종료 직후 복사한 Godot 원본은 `536_balance_boss_input_sync_1.raw.log`/`input_sync_2.raw.log`와 각각 `.godot.raw.log`, 비교는 `._tmp/536_balance_boss_input_sync_comparison.raw.log`에 남긴다. 이 값은 통합 전체 balance_boss의 RNG/승패/공격/명중 대조 기준이다.

**게임의 모든 시각·좌표까지 결정적이라고 주장하지 않는다.** Lv3 P2는11.2/11.1초, Lv5 P2는14.7/14.6초·종료27.8/27.7초·입력 확인 횟수278/277로 달랐다. Lv5의 준비 상대 틱과 파수XZ는 같지만 V 뒤 타깃 좌표는(10.5,9.5)/(10.5,8.5)였다. MP/쿨다운의 `_process`와 animation impact 콜백 등 게임의 화면 프레임 처리는 유지했다. 남은0.1초/좌표 차이를 없애려고 시드·틱 수·게임 AI/타이머·판정을 더 고치지 않았다. 원래 GameClock 최소/최대 시간 판정은 양쪽 모두 통과했다.

이전 과정도 제외하지 않는다. RNG만 고정한 `focus_1/2`는22검사씩 통과했지만 Lv5 파수2 종료 state와 공격/명중이 달랐다. read-only `diag_1`은 추격·돌진 접촉과 process 준비 물리 틱 차이를 드러냈다. 준비6/5틱의 `sync_1/2`는28검사씩 통과했지만 Lv3 파수2 final과 공격41/40이 달랐다. 전투6틱의 `combat_sync_1/2`는30검사씩 통과했지만 입력 버퍼로 실제 층 ready가 한 틱 달랐고 Lv5 파수 둘 final·공격30/34·명중20/22가 달랐다. 각 stdout/Godot raw와 비교 raw를 모두 보존했다. 단위 보완 과정의 class_name/오토로드 컴파일 실패, PREDELETE 정리 실패, release 전달 전 InputEvent probe 실패도 `536_balance_rng_unit_guard_*`, `536_balance_rng_combat_unit*`, `536_balance_rng_input_sync_unit` raw 전문에 남겼다. 첫 focused 잠금 대기 취소는 `536_balance_boss_pre_guard_wait_only.raw.log`에 남아 있으며 전투 미실행이다. 시드 검색·세 판 기준 확장·실패 전투 삭제는 하지 않았다.
